Inside the switch

How a P4sim switch works

Four animated walkthroughs, drawn from the P4sim design figures and checked against its code: where the switch sits in ns-3, how a packet travels through the pipeline, how the queues and the scheduler decide which packet leaves next, and how custom headers cross the network. Chapter 1 · Switch model

A P4 switch inside ns-3

A control plane programs the tables; the data plane runs every packet through the P4 program.

  1. P4SwitchNetDevice is installed on an ns-3 node like any other device. Here its ports are bridge ports, the node's CSMA or point-to-point devices, so hosts and other switches attach over ordinary ns-3 links. Since 2.0 a switch can also own switched-Ethernet ports.

  2. Rules arrive through the control-plane interface: runtime CLI commands over Thrift at start-up, or P4Controller calls during the run. Here a rule sends 10.1.1.2 to port 3.

  3. Host 1 sends a packet to 10.1.1.2. The switch hands it to its BMv2 core, whose parser splits the bytes into header fields.

  4. The table ipv4_nhop looks up ipv4.dst. The rule installed a moment ago matches, and its action sets the egress port to 3.

  5. The deparser turns the fields back into bytes, and the packet leaves port 3 on an ns-3 link to Host 2. Every step ran the real P4 program.

Chapter 2 · Pipeline and queues

Through the pipeline

From the input buffer to the egress port: parsing, match-action stages, the traffic manager's priority queues, and the loops a P4 program can take.

  1. The compiled P4 program defines the parser graph, the control flow, the actions and the tables. ns-3 attributes set the buffer sizes, an optional packet rate and latency of the pipeline (SwitchRate, PipelineDelay) and the ports.

  2. An arriving packet joins the input buffer. Packets from outside wait in one queue; resubmitted and recirculated packets have their own, higher-priority queue. They wait only while the pipeline is busy, which happens only when SwitchRate limits it.

  3. The parser follows the parse graph of the P4 program and extracts the headers into the packet header vector (PHV).

  4. Stage by stage, ingress tables read the PHV and run actions, with tables, registers and counters as state. Here they set the egress port to 3 and the priority to 5.

  5. The packet joins queue 5 of port 3, after PipelineDelay if one is set. Whenever port 3 has sent a frame, it takes the next packet, highest queue first: the packet in queue 7 leaves before ours. Chapter 3 looks at the queues closely.

  6. The egress runs when port 3 takes the packet. Egress tables can still rewrite it; the deparser turns the PHV back into bytes, and port 3 sends the frame at its link's data rate. V1model parses once and deparses at the end; PSA adds a deparser after ingress and a parser before egress.

  7. A program can also resubmit a packet to ingress, recirculate it after egress, clone it (ingress-to-egress or egress-to-egress), or send multicast copies to several ports.

Chapter 3 · Queues and scheduling

Which packet leaves next?

A closer look at the output queues of a port: eight priority queues, a port that takes its next packet when it is free, per-queue rate limits, full queues, and the input buffer before the pipeline. Below the walkthrough, a live model lets you try it.

  1. Host 0 sends three UDP flows to Host 1. The P4 program qos.p4, from the example p4-queue-test, matches the UDP destination port in the table udp_priority and sets standard_metadata.priority: port 2000 gets priority 1, port 3000 priority 2, port 4000 priority 3.

  2. Every egress port has eight output queues, and priority p goes to queue p. On the way in, the switch writes enq_timestamp and enq_qdepth into the packet's metadata. Host 0's link runs at 1 Gbps and port 1's at 100 Mbps, so packets arrive up to ten times faster than port 1 can send them, and the queues fill.

  3. Port 1 sends one frame at a time: a 1042-byte frame (1000 bytes of payload) takes 83.36 µs at 100 Mbps. When its last bit has left, the port takes the next packet, from the highest queue whose head is ready, and runs it through the egress. Each port takes its own packets, so a busy port does not slow down the others.

  4. By default the queues have no rate limit, so the port serves them in strict priority. While queue 3 always has a packet ready, it wins every time the port is free, and the packets in queues 2 and 1 keep waiting.

  5. A queue can have its own rate, set with set_queue_rate in the flow table or SetEgressPriorityQueueRate. Here queue 3 is limited to 6 000 packets per second, one every 166.7 µs or two frame times. When its next packet is not due yet, the port takes a lower queue, so flows 2 and 1 get through.

  6. Each queue holds QueueBufferSize packets, 128 by default (6 in this picture). A packet that finds its queue full is dropped at once.

  7. When the port takes a packet, the switch writes deq_timedelta (the time in the queue, in nanoseconds in P4sim), deq_qdepth and qid, which egress code can read, for example to mark congestion. The deparser builds the frame, and the port puts it on the wire. By default nothing waits after the egress, so the backlog stays in the priority queues; TransferBufferSize adds a small FIFO there, like the port queue of a hardware switch.

  8. SwitchRate (0 by default: no limit) models a slower switch, such as a software switch: the pipeline takes one packet per 1 / SwitchRate. Packets that arrive meanwhile wait in the input buffer, in arrival order and without priorities, and are dropped when it is full (InputBufferSizeLow, 128 packets). Here SwitchRate is 10 000 packets per second, one per 100 µs.

    Chapter 4 · Custom headers

    Custom headers across the network

    Hosts in ns-3 can carry a header of your own design, so P4 programs such as tunnels have something to parse and match.

    Custom header position

    1. Host 1's ns-3 stack builds Ethernet, IPv4 and UDP headers. Each header's type field names the next one: etherType 0x0800 means IPv4.

    2. A CustomHeader is a list of named fields with bit widths, plus a layer and an operator that say where it goes. From the p4-basic-tunnel example:

      CustomHeader h;
h.SetLayer(HeaderLayer::LAYER_3);
h.SetOperator(ADD_BEFORE);   // before IPv4
h.AddField("proto_id", 16);
h.AddField("dst_id", 16);
device->SetCustomHeader(h);

    3. CustomP2PNetDevice inserts the header and rewires the chain: the type field in front of it becomes 0xDC, P4sim's custom protocol number, and the custom header records which protocol followed, so the original packet can be restored.

    4. On the way, a P4 switch sees the 0xDC type and its parser extracts the custom header. Tables can then match on its fields: basic_tunnel forwards on dst_id.

    5. The receiving CustomP2PNetDevice walks the headers, drops the custom one, restores the original type field and passes an ordinary packet to its IPv4 stack.
